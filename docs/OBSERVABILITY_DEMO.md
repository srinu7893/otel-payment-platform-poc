# Observability Demo Runbook

## Goal

Demonstrate a realistic payment microservice platform with real telemetry generated by backend services, not mocked dashboard data.

## Start

```bash
cp .env.example .env
docker compose up --build -d
```

Application:
- Frontend: http://localhost:3000
- API Gateway: http://localhost:8088

Observability:
- Grafana: http://localhost:3001
- Jaeger: http://localhost:16686
- Prometheus: http://localhost:9090
- OTel Collector health: http://localhost:13133

Grafana local credentials:
- username: admin
- password: admin

## Architecture

```text
Browser
  |
  v
API Gateway
  |
  +--> Auth
  +--> Customer
  +--> Payment
          |
          +--> Gateway Service
          |       |
          |       +--> Mock Bank
          |
          +--> PostgreSQL
          |
          +--> Outbox --> RabbitMQ --> Notification

Every Java service
  |
  +--> OpenTelemetry Java Agent
          |
          +--> OTLP
                |
                v
          OTel Collector
             /      \
        traces      metrics
          |            |
        Jaeger      Prometheus
             \       /
              Grafana
```

## Recommended manager demo

### 1. Show the application first

Login with:

```text
demo / demo123
```

Create a normal merchant payment.

Explain:
- authenticated CUSTOMER request
- source-account ownership
- risk validation
- payment PROCESSING state
- Gateway -> Mock Bank
- bank ledger/idempotency
- local finalization
- transactional outbox
- RabbitMQ notification

Then show the successful payment and notification in the UI.

### 2. Show the distributed trace

Open Jaeger and select `api-gateway`.

Find a recent `POST /api/v1/payments` trace.

Expected services in the synchronous flow:

```text
api-gateway
  -> payment-service
      -> customer-service
      -> gateway-service
          -> mock-bank-service
      -> PostgreSQL spans
```

Point out:
- service boundaries
- request latency
- downstream HTTP calls
- JDBC spans
- errors/status
- trace ID

### 3. Show log correlation

Run:

```bash
docker compose logs --no-color payment-service gateway-service mock-bank-service | grep trace_id | tail -20
```

Structured logs include:

```text
correlationId
trace_id
span_id
paymentId / transferId / refundId
event
status
```

Explain that support can move from a business/correlation ID to the distributed trace.

### 4. Show metrics

Open Grafana at http://localhost:3001.

Dashboard:
`Payment Platform - OTel Overview`

Show:
- services emitting HTTP metrics
- request rate by service
- p95 HTTP latency
- JVM heap usage

Prometheus can be opened directly if you want to demonstrate raw metrics/querying.

### 5. Show asynchronous messaging

Create a payment or P2P transfer and wait for its notification.

Explain:

```text
Payment transaction
  -> transactional outbox
  -> scheduled relay
  -> RabbitMQ
  -> Notification consumer
  -> notification DB
```

The Java agent instruments supported RabbitMQ activity, while the application keeps the business correlation ID in message headers.

### 6. Show a failure trace

Use the preconfigured slow customer:

```text
slowdemo / slowdemo123
```

Create a payment from `ACC-SLOW`.

Expected business outcome:

```text
PROCESSING
  -> downstream timeout/circuit protection
  -> outcome UNKNOWN
  -> RECONCILIATION_REQUIRED
  -> scheduled reconciliation
```

Then inspect the trace in Jaeger and compare latency with a normal payment.

This is a strong demo because it shows why observability matters rather than only showing a dashboard.

### 7. Show a downstream error

Use:

```text
errordemo / errordemo123
```

Payment from `ACC-ERROR` produces a simulated downstream failure and moves safely into reconciliation rather than incorrectly claiming the financial outcome is final.

The single GitHub Actions workflow validates:

1. backend unit/integration/Testcontainers tests
2. frontend production build
3. Docker Compose validity/build
4. service startup/health
5. payment/P2P/refund/risk/outbox smoke
6. pre-OTel slow/error reconciliation scenarios
7. OTel backend health
8. all seven services visible in Jaeger
9. payment-service metrics visible in Prometheus
10. Grafana health
11. trace IDs injected into structured logs

Run locally:

```bash
bash scripts/otel_acceptance.sh
```

## Talking points

- No application-code instrumentation was required for the first pass; Java Agent auto-instrumentation gives broad HTTP/JDBC/Rabbit/JVM coverage.
- The Collector decouples applications from the backend vendor.
- Local Jaeger/Prometheus/Grafana can later be replaced by GCP/Splunk/Tempo without rewriting every service.
- Business logs already carry payment/transfer/refund IDs and correlation IDs.
- We intentionally do not put passwords, JWTs, secrets or full account identifiers into telemetry.
