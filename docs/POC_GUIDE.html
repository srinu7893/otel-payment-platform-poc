Manager overview

A simulated payment platform demonstrating synchronous HTTP calls, database transactions, durable asynchronous delivery and OpenTelemetry across seven Java services. No real money, bank, SMS or email providers are involved.

This increment implements the local observability stack and executable acceptance gates. Configuration and source presence do not prove runtime success: use the Evidence section to see what actually ran. GCP deployment and production hardening remain separate decisions.

Happy path: browser → API Gateway → Payment → Customer ownership check → Gateway adapter → Mock Bank → bank ledger. Payment state and outbox event are committed together. A scheduled relay restores saved W3C context, opens outbox.publish, sends via RabbitMQ and waits for publisher confirm. Notification consumes and persists a deduplicated simulated delivery.

The relay keeps traceparent and tracestate in nullable V6 migration columns. Existing events without context create new roots. Baggage is deliberately not persisted. Agent instrumentation handles HTTP, JDBC and messaging; only the durable scheduling boundary needs explicit context restoration. Retries after long outages can appear later than the original request, so widen the trace/log time window.

Telemetry path: every Java process exports OTLP/HTTP → Collector. Traces go to Tempo; logs to Loki native OTLP; application metrics are exposed by the Collector for Prometheus scraping. Tempo produces span metrics and service graphs into Prometheus via remote write. Grafana reads all three backends.

Recreate locally

Prerequisites: Git, Java 21, Maven, Docker with Compose v2, Python 3, curl, jq and sha256sum. Allow roughly 12 GB RAM for a comfortable local demo. Containers and dependencies need internet access on first build. Use a fresh disposable stack for deterministic tests; fixed smoke-test IDs and bank balances make reusing old state unsuitable.

git clone https://github.com/srinu7893/otel-payment-platform-poc.git
cd otel-payment-platform-poc
# Before merge, select the implementation branch:
git checkout feature/otel-observability-manual-e2e
export COMPOSE_PROJECT_NAME=otel-demo
mvn -B clean verify
bash scripts/setup-otel-agent.sh
bash scripts/otel-compose.sh config --quiet
bash scripts/otel-compose.sh run --rm --no-deps otel-collector validate --config=/etc/otelcol/config.yaml
bash scripts/otel-compose.sh run --rm --no-deps --entrypoint promtool prometheus check config /etc/prometheus/prometheus.yml
bash scripts/otel-compose.sh up --build -d
bash scripts/e2e/wait-ready.sh

Backend Dockerfiles copy packaged target/*.jar; building with Maven first is required. The frontend container builds its own bundle. Starting without docker-compose.otel.yml keeps the original baseline agent-free.

Manual automated acceptance

GitHub → Actions → manual-otel-e2e → Run workflow. Select the intended ref and choose whether to include broker/Collector outages. workflow_dispatch must first exist on the default branch to appear in the Actions UI. Ordinary CI retains backend tests and build validation, but does not start the stack or run E2E.

For local testing, keep the same COMPOSE_PROJECT_NAME used at startup. The resilience option stops only that Compose project’s demo broker/Collector. Run scripts in this order on fresh state:

bash scripts/e2e/business-smoke.sh
RESILIENCE=true python3 scripts/e2e/otel_acceptance.py
bash scripts/pre_otel_acceptance.sh
python3 scripts/render-poc-guide.py

The manual workflow runs Maven unit and Testcontainers integration tests, validates backend configs, builds/starts the stack, checks business success/failure paths, queries real telemetry backends, collects diagnostic logs and always removes its disposable stack. Evidence artifact: otel-poc-evidence-<run number>. Includes Surefire reports, actual OTel assertion results, trace ID summary, Compose logs and this HTML. A failed test fails the workflow; missing telemetry is not treated as a skipped success.

Manual manager demonstration

  • Open the customer UI and sign in as demo / demo123. Create a small merchant payment using ACC1001. Note its payment ID and confirm COMPLETED.
  • Sign in as support / support123 in another browser session. Open the operations dashboard and verify service health. Use the Observability card to open Grafana.
  • In Grafana Explore choose Loki and search 
    {service_name="payment-service"} |= "PAYMENT_ID"
    Replace PAYMENT_ID with the actual ID. Expand the log metadata; open trace_id in Tempo. Follow edge → payment → customer/gateway → bank → JDBC, then outbox.publish → RabbitMQ → notification.
  • Explain request duration versus eventual notification delay. The async consumer can finish after the HTTP response. Examine parent spans, database duration and service map rather than summing overlapping durations.
  • Refund the completed payment. Check refund history and PAYMENT_REFUNDED notification. Replay via the smoke script and explain bank-side idempotency and consumer deduplication.
  • Use amount 6000 on a fresh ACC1001 balance to demonstrate insufficient funds. Use 100001 for configured transaction-risk rejection. Explain why a business failure can return HTTP 2xx and why HTTP error graphs alone are insufficient.
  • Use slowdemo / slowdemo123 with ACC-SLOW and errordemo / errordemo123 with ACC-ERROR for timeout/500 scenarios. Confirm reconciliation state, inspect downstream error/latency spans and distinguish unknown outcome from decline.
  • Run the optional resilience suite. Show outbox failure counters and recovery after broker restart. Show application availability during Collector outage, then fresh traces after recovery.
  • Finish with the workflow evidence artifact and Evidence section below. Demonstrate passed assertions from an actual run; label any unexecuted scenario explicitly.

Developers add business spans around meaningful work using the OpenTelemetry API supplied by the agent; do not install a second SDK or tracing starter alongside it. Use bounded dimensions such as outcome and operation. Never use payment IDs, account numbers, email, JWT or raw URL values as metric labels. The custom outbox metric counts publish attempts confirmed by the broker, not unique committed payments; database rollback and retry can increase it.

# Loki: operational failures
{service_name="payment-service"} |~ "PAYMENT_(NOT_COMPLETED|RECONCILIATION_REQUIRED)"
# Loki: exact known trace
{service_name=~".+"} | trace_id="REPLACE_WITH_TRACE_ID"
# Tempo TraceQL: bank errors
{ resource.service.name = "mock-bank-service" && status = error }
# Prometheus: HTTP p95 (seconds)
histogram_quantile(0.95, sum by (le,service_name) (rate(http_server_request_duration_seconds_bucket[5m])))
# Prometheus: outbox publish failures
sum(increase(poc_outbox_publish_attempts_total{outcome="failure"}[5m]))

docker compose -f docker-compose.yml -f docker-compose.otel.yml -f docker-compose.sampling.yml   run --rm --no-deps otel-collector validate --config=/etc/otelcol/config.yaml --config=/etc/otelcol/tail.yaml

# After experimentation, restore full-trace acceptance configuration:
bash scripts/otel-compose.sh up -d --force-recreate otel-collector

Tail sampling waits 30 seconds and retains errors, latency over 2 seconds, and a 10% baseline. Late outbox retries can exceed this decision window; evaluate span links or a larger window before production. Service-graph/span-rate metrics derived after sampling describe sampled traffic, not total traffic; use unsampled application metrics for accurate request SLOs.

Review findings and remaining decisions

  • Fixed: transaction outbox lacked durable trace context. V6 adds nullable traceparent/tracestate and the relay restores request context around publish.
  • Fixed: full-stack smoke and pre-OTel acceptance ran on ordinary CI. They now live in a manual-only workflow, along with telemetry and resilience assertions.
  • Fixed: no telemetry backends or operational trace/log entry point. The overlay provisions all three signal paths and support UI links.
  • Known baseline boundary: internal customer/bank endpoints rely on trusted-network deployment; demo JWT secrets/accounts and exposed service ports must not be deployed publicly. See docs/SECURITY_BASELINE.md and docs/SERVICE_IDENTITY_STRATEGY.md.
  • Pending verification: runtime agent/library compatibility, backend configurations, dashboard query results and complete live acceptance must be proven by the manual run. Local source/static checks alone do not establish these.
  • Production scope: choose GCP runtime, backend/vendor, IAM/secrets, retention/cost, broker management and support escalation policy. All OpenTelemetry ecosystem features cannot meaningfully be declared complete by one local PoC.
