Why OpenTelemetry helps this payment platform

The main demonstration is an investigation: take a payment ID, find its business log, follow the trace across services and asynchronous delivery, then use metrics to see whether the same problem affects other requests. The instrumentation turns separate service activity into evidence that developers and production support can navigate.

SignalWhat it tells youWhat this PoC displays
Logs — eventsWhat happened and which business operation it affected.Payment outcome, risk decision, bank failure, outbox retry and notification events in Loki.
Traces — one requestWhere time was spent and which dependent operation failed. A span represents one operation; trace IDs connect related spans.HTTP, JDBC, outbox.publish and RabbitMQ consumer spans in Tempo, with service, duration, status and parent relationships.
Metrics — trendsHow often something happens and whether latency, errors or resource usage are increasing.HTTP rate/errors/p95, JVM memory, outbox publish attempts, service graph rates and telemetry target health in Prometheus/Grafana.

OpenTelemetry generates, collects, processes and exports telemetry. In this PoC, Loki stores logs, Tempo stores traces, Prometheus stores metrics and Grafana displays them. Business log messages still come from application code; the Java agent captures them with service and active trace/span context. A healthy endpoint alone cannot establish that a payment or eventual notification succeeded.

Inside our microservices: how telemetry is generated

The integration begins at JVM startup, not inside Grafana. docker-compose.otel.yml mounts the checksum-verified Java agent into each of seven backend containers and supplies JAVA_TOOL_OPTIONS. The JVM loads the agent before the application; it instruments supported framework/library calls. Our observed HTTP, JDBC and RabbitMQ spans prove those library paths are instrumented. It does not trace every Java method or invent business outcomes.

The durable outbox boundary needs explicit work

The payment request and its outbox event are committed together. OutboxTraceContext captures only W3C traceparent/tracestate into nullable Flyway V6 columns. The later scheduler is a different execution context: OutboxRelay restores the saved parent, creates outbox.publish, makes it current, publishes through RabbitTemplate and waits for broker confirmation. Agent messaging instrumentation continues the producer/consumer context into Notification. The span ends in finally; failures record an exception/error status and a failure attempt. Legacy or invalid saved context creates a new root. Arbitrary baggage and credentials are not persisted.

request Context → outbox traceparent/tracestate columns
scheduler → restore saved Context → outbox.publish.makeCurrent()
RabbitTemplate publish → agent message propagation → notification consumer

X-Correlation-Id is our human-facing operational identifier. traceparent carries W3C trace/span context; they are different fields. A payment ID identifies the business transaction, while a trace ID identifies one related execution. Retries or reconciliation may create later executions, so keep the business ID and widen the time range.

The SDK represents a trace as spans grouped by Resource and instrumentation Scope. A resource identifies the JVM/service; a scope identifies the library emitting telemetry. OTel log records carry body/severity/timestamp/context fields; the console JSON wrapper is a separate output format. Metrics carry instrument names, units, attributes and timestamped number/histogram points. These structured objects become protobuf OTLP requests; Grafana never runs the Java instrumentation.

Inside the Collector: receive, process, queue and export

The Collector is a separate Go process. Each JVM pushes an OTLP protobuf payload over HTTP to port 4318. The receiver exposes /v1/traces, /v1/metrics and /v1/logs, decodes the signal into the Collector’s telemetry representation and hands it to the corresponding configured pipeline. Port 4317 also accepts OTLP gRPC, although our JVM configuration uses HTTP/protobuf. The receiver does not scrape Java logs or magically inspect the application database.

Collector queue storage runs as UID 10001. A one-shot volume initializer prepares permissions; it does not delete queued data. The crash experiment stops Tempo/Loki, queues a real payment’s telemetry, SIGKILLs/restarts the Collector, restores the backends, then requires the same connected trace and logs and a drained queue. Its observed result is in Evidence; configuration alone is not treated as a successful durability test.

Receivers decode OTLP into the Collector’s internal telemetry representation and invoke the configured pipeline in order. A successful OTLP response is not a receipt proving backend storage. The batch processor can accept data into memory before the persistent exporter queue; an abrupt crash can still lose that pre-queue data. File-backed queues improve recovery for requests already enqueued, and eligible failures are retried. Queue recovery is not an exactly-once telemetry guarantee.

Health endpoint :13133 reports Collector process availability. Internal metrics reveal whether it is accepting signals or failing exports. Logs are emitted as JSON to stderr for diagnosis without depending on Loki. There is no live automatic application-log file receiver or infinite retry queue.

Backend storage, Grafana and a runnable query lab

Grafana queries provisioned datasources through its server-side proxy. It displays stored data; it does not generate application telemetry. Tempo returns trace/span data, Loki returns logs or log-derived counts, and Prometheus returns metric time series. Service graphs are derived from matching span relationships; they do not automatically prove every architectural dependency or a business outcome. Native OTLP Loki ingestion retains log attributes as structured metadata; service labels narrow streams while trace IDs are filtered as metadata.

The Prometheus exporter translates OTel instruments to Prometheus series, including normalized names/units and histogram bucket/count/sum series. Prometheus records each scrape in its TSDB. How an enterprise would operate and extend this design

The following is a deployment plan, not a claim that this single-node demo already provides cloud HA, identity or paging. Five-minute explanation you can give your manager

  • Our Java agent instruments supported calls inside each backend and exports three signals. Application events supply the business meaning.
  • A W3C trace ID follows synchronous calls. We persist its parent context in the database outbox because notification delivery happens later on another thread/process.
  • The Collector receives OTLP, applies common resource/privacy/memory/batch policy, then queues/exports traces and logs. Prometheus pulls exposed metrics.
  • Tempo stores request traces, Loki stores event logs and Prometheus stores time series. Grafana queries them and connects an incident graph to related logs and spans.
  • The manager demo follows a successful payment, a slow/error payment and a broker outage. We show the customer outcome, log evidence, responsible dependency, trend/alert and safe operational action.
  • The manual suite verifies the real integrations and recovery behavior. Enterprise deployment adds identity, HA/storage, SLO ownership, cost controls and paging, each with its own acceptance gate.

Workload identity and secrets

Application Authorization: Bearer <customer JWT> is preserved. The Cloud Run caller supplies X-Serverless-Authorization: Bearer <Google ID token> with the target's canonical service origin as audience. Tokens come from the fixed metadata endpoint, are checked for audience/lifetime and cached with a 60-second refresh margin. A fixed deployment-configured audience allowlist prevents sending workload credentials to an arbitrary destination. Reactive gateway/probe token work runs outside the Netty event loop. Caller-provided workload headers are replaced. Local IAM mode is disabled.

Each target needs roles/run.invoker for only its actual callers. The gateway calls all six services for support health probes; ordinary routes call auth/customer/payment/notification. Payment calls gateway/customer; gateway calls bank. Private health verification impersonates the target runtime service account, so that account must also have self-invoker permission. Only frontend and api-gateway have allUsers invoker. IAM-protected backends retain ingress=all for canonical service-to-service HTTPS; an internal-ingress design requires separately validated VPC routing and is not claimed here.

Runtime Java service accounts require roles/cloudtrace.agent, roles/logging.logWriter and roles/monitoring.metricWriter. Grant Secret Manager access only to each service's required secret versions; frontend needs none. Deployment identity requires Artifact Registry write, Cloud Run release permissions, actAs on runtime accounts, and the narrowly scoped impersonation permission used for health checks. WIF trust must restrict this repository, intended branch/environment and deployment identity. Enable Run, Artifact Registry, IAM Credentials, Secret Manager, Logging, Trace and Monitoring APIs. Cloud SQL/VPC resources and access require separate provisioning.

config.example.json contains names and URLs, not secret values. JDBC URL, DB username/password, Rabbit username/password and JWT secret are referenced from pinned numeric Secret Manager versions. The JDBC URL must use a correctly configured encrypted/verified database connection; this increment does not install a Cloud SQL JDBC connector or CA mount. Rabbit TLS trust must match the managed provider's certificate. Neither private networking nor TLS alone establishes a complete production security review. Seeded demo users/bank accounts are for isolated demonstrations, never a real payment service.

Production support triage, from report to verification

  1. Record the affected business ID, UTC start/end window, customer-visible outcome, correlation/trace ID and deployed source version. Preserve idempotency keys for reconciliation. Collect only the minimum permitted synthetic/business identifiers; never paste tokens, credentials or full sensitive payloads into an incident ticket.
  2. Establish impact. Check ingress request rate/5xx/latency, technical SLO windows and Cloud Run capacity/cold starts. Then check business completion/reconciliation logs and notification backlog/DLQ. A green HTTP availability chart cannot establish that money movement or eventual delivery succeeded.
  3. Find the event by business ID, then the exact trace. Inspect server/client/JDBC/outbox/consumer parent relationships and elapsed time. Follow the critical path; overlapping spans cannot simply be added. A successful span or HTTP 200 can coexist with a declined/unknown business result. Trace sampling and async export mean missing spans are not proof that work never occurred.
  4. Separate application trouble from telemetry trouble. If data is absent, check receiver accepted/refused counts, export errors, queue occupancy/capacity, backend availability, scrape/auth permissions, time range and sampling. Local collector-ingress.json, collector-queues.json, Prometheus targets and sidecar/cloud logs provide distinct evidence. Sidecar readiness only proves its health endpoint responds.
  5. Choose a bounded action. For broker trouble, restore broker connectivity and verify the persisted outbox catches up with duplicate-safe notification delivery. For an unknown bank outcome, reconcile the original operation; do not create a fresh financial retry ID. For poison events, inspect DLQ cause/ownership and redrive deliberately. For a bad release, restore the saved traffic split, then separately assess migrations and background work already performed.
  6. Verify recovery with a uniquely keyed small fake payment, completed domain status, eventual SENT notification, stored correlated logs, a distributed trace, exported metrics and a draining backlog. Check both the particular transaction and aggregate trend windows. Capture actual results before closing the incident; a service restart alone is not a recovery test.
  7. Produce an incident record: impact/window, source revision, symptom, evidence/query links, suspected versus confirmed cause, action, verification and follow-up owner. Preserve the guide/evidence against the tested revision and revisit alert thresholds/privacy/sampling when behavior changes. Pager escalation, incident ownership and production access controls require the team's own configuration.

BigQuery query templates

-- Linked Cloud Logging dataset schema, not the schema of a direct export sink.
-- Replace PROJECT_ID and LINKED_DATASET, inspect your view schema and set query budgets.
-- 1. Raw application logs in a bounded period. Keep structured fields for investigation.
SELECT timestamp, severity, log_name, resource, trace, span_id, insert_id,
       text_payload, json_payload
FROM `PROJECT_ID.LINKED_DATASET._AllLogs`
WHERE timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR)
  AND log_name = 'projects/PROJECT_ID/logs/payment-poc-otel'
ORDER BY timestamp DESC
LIMIT 1000;

-- 2. Ordered raw events for one execution across services. Replace TRACE_ID.
SELECT timestamp, severity, resource, span_id,
       COALESCE(text_payload, JSON_VALUE(json_payload, '$.message'), TO_JSON_STRING(json_payload)) AS message
FROM `PROJECT_ID.LINKED_DATASET._AllLogs`
WHERE timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 DAY)
  AND log_name = 'projects/PROJECT_ID/logs/payment-poc-otel'
  AND trace = 'projects/PROJECT_ID/traces/TRACE_ID'
ORDER BY timestamp ASC
LIMIT 1000;

-- 3. Hourly emitted business events. These are log event counts, not unique transactions.
WITH events AS (
  SELECT timestamp,
         REGEXP_EXTRACT(COALESCE(text_payload, JSON_VALUE(json_payload, '$.message'),
                                TO_JSON_STRING(json_payload)), r'event=([A-Z_]+)') AS event
  FROM `PROJECT_ID.LINKED_DATASET._AllLogs`
  WHERE timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
    AND log_name = 'projects/PROJECT_ID/logs/payment-poc-otel'
)
SELECT TIMESTAMP_TRUNC(timestamp, HOUR) AS hour, event, COUNT(*) AS emitted_events
FROM events
WHERE event IS NOT NULL
GROUP BY hour, event
ORDER BY hour DESC, emitted_events DESC
LIMIT 1000;
